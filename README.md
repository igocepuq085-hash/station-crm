# station-crm

MVP-сервис для начальника службы погрузки и маневровых работ. Он помогает открыть веб-дашборд и увидеть, как прошла работа станции за сутки: какие отчеты загружены, какие листы найдены, какие строки содержат важные слова и где лежит сырой слой данных для будущих KPI.

## Назначение MVP

Сервис работает с суточным комплектом отчетов станции:

- оперативный Excel;
- вагонный Excel.

PDF больше не является обязательным входным файлом: данные справки вагонов берутся из вагонного Excel, прежде всего из вкладки `Отчет НС`.

Главная технологическая цепочка проекта:

```text
Сургут -> прибыло на Промышленную -> обработано на Промышленной -> погружено -> оформлено -> отправлено в Сургут
```

В текущей версии MVP сервис сохраняет исходные файлы, создает комплект отчетов, извлекает из Excel список листов и строки по ключевым словам, а затем показывает результат на дашборде.

## Что умеет MVP

- Загружает комплект из двух обязательных файлов: оперативный Excel и вагонный Excel.
- Сохраняет файлы в `storage/uploads`.
- Автоматически определяет тип отчета: `operational_excel`, `wagons_excel`.
- Создает запись комплекта отчетов в SQLite.
- Извлекает из Excel список листов, размер листов и строки с ключевыми словами.
- Сохраняет найденные строки в таблицу `raw_extracted_rows`.
- PDF-парсер оставлен как необязательный технический слой, но штатная загрузка работает без PDF.
- Показывает дашборд комплекта со статусом, файлами, листами, найденными строками и заготовками KPI.
- Показывает комплектность: найден ли оперативный Excel и вагонный Excel.
- Строит MVP-аналитику технологической цепочки и KPI по извлеченным строкам.
- Строит продуктово-вагонную аналитику: продукт, группа, план, наличие продукта, подходящие вагоны, годность, погрузка, оформление и отправление.
- Показывает управленческие графики на dashboard через Chart.js.
- Формирует rule-based управленческий вывод по каждому комплекту.
- Показывает страницу `/trends` с динамикой по всем загруженным комплектам.
- Показывает сырой слой данных на странице `/raw/{package_id}` с фильтрами по ключевому слову и листу.

## Локальный запуск

Рекомендуется использовать отдельное виртуальное окружение:

```bash
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
uvicorn main:app --reload
```

По умолчанию приложение использует локальную SQLite-базу `storage/station_crm.db`.

Откройте в браузере:

- `http://127.0.0.1:8000/login` - вход;
- `http://127.0.0.1:8000/upload` - загрузка комплекта отчетов.
- `http://127.0.0.1:8000/trends` - тренды по всем загруженным комплектам.
- `http://127.0.0.1:8000/raw/{package_id}` - сырой слой загруженного комплекта.

Дефолтный локальный логин из `.env.example`:

- логин: `admin`
- пароль: `admin`

Перед реальным использованием смените `ADMIN_PASSWORD` и `APP_SECRET_KEY`.

## Загрузка отчетов

1. Откройте `/login` и войдите под администратором.
2. Перейдите на `/upload`.
3. Укажите дату отчета и при необходимости комментарий.
4. Загрузите два файла: оперативный Excel и вагонный Excel.
5. После обработки сервис перенаправит на `/dashboard/{package_id}`.
6. Сырой слой доступен на `/raw/{package_id}`, общая динамика - на `/trends`.

## Запуск на Railway

Проект подготовлен для Railway:

- `runtime.txt` фиксирует Python `3.12`;
- `Procfile` содержит web-команду запуска;
- `railway.toml` содержит `startCommand`;
- если задан `DATABASE_URL`, SQLAlchemy подключается к PostgreSQL;
- если `DATABASE_URL` не задан, используется локальная SQLite.

Минимальные шаги:

1. Создайте проект на Railway из репозитория.
2. Добавьте PostgreSQL plugin/service.
3. Убедитесь, что переменная `DATABASE_URL` доступна приложению.
4. Добавьте переменные `APP_SECRET_KEY`, `ADMIN_USERNAME`, `ADMIN_PASSWORD`.
5. Запустите deploy.

Команда запуска на Railway:

```bash
uvicorn main:app --host 0.0.0.0 --port $PORT
```

Важно: файловое хранилище Railway может быть эфемерным. Для production-хранения исходных отчетов позже стоит подключить внешнее object storage. Для MVP файлы сохраняются в `storage/uploads`.

## Переменные окружения

```env
DATABASE_URL=
APP_SECRET_KEY=change-me
ADMIN_USERNAME=admin
ADMIN_PASSWORD=admin
STORAGE_PATH=storage
USE_AI_SUMMARY=false
USE_AI_EXTRACTION=false
OPENAI_API_KEY=
OPENAI_MODEL=gpt-5.4-nano
```

- `DATABASE_URL` - если задан, используется PostgreSQL; если пустой, используется SQLite.
- `APP_SECRET_KEY` - ключ подписи session-cookie, обязателен для Railway.
- `ADMIN_USERNAME` - логин администратора.
- `ADMIN_PASSWORD` - пароль администратора.
- `STORAGE_PATH` - путь для сохранения загруженных файлов; на Railway с volume используйте `/app/storage`.
- `USE_AI_SUMMARY` - `true` включает OpenAI-вывод, `false` оставляет rule-based вывод.
- `USE_AI_EXTRACTION` - `true` включает AI-разбор найденных строк отчета, `false` отключает его.
- `OPENAI_API_KEY` - ключ OpenAI API, необязателен.
- `OPENAI_MODEL` - модель для AI-вывода и AI-разбора, по умолчанию `gpt-5.4-nano`.

## Структура данных

База SQLite создается автоматически в `storage/station_crm.db`.

Alembic в MVP не подключен: таблицы создаются при старте приложения через SQLAlchemy.

Сырой слой данных удалять нельзя. Все будущие нормализованные показатели и расчеты должны сохранять ссылку на источник: файл, лист, строку и, когда возможно, ячейку.

Основные таблицы сырого слоя:

- `report_packages` - комплект отчетов за дату;
- `report_files` - исходные файлы комплекта, путь хранения, тип, хеш и статус;
- `parsed_sheets` - найденные Excel-листы и их размеры;
- `raw_extracted_rows` - строки, найденные по ключевым словам;
- `raw_metrics` - заготовка для будущих нормализованных метрик с привязкой к источнику.
- `daily_chain_metrics` - агрегированная строка MVP-воронки за сутки или смену.
- `product_wagon_metrics` - продуктово-вагонные показатели с учетом соответствия продукта и вагонов под продукт.

Тип отчета сохраняется в `report_files.detected_report_type`.

- `operational_excel` определяется по листам: `Сводка диспетчера ДО`, `Приложение №3а`, `Перевалка`, `УПГ`, `Томск`, `Новый Уренгой`, `ПЕРЕХОДЯЩИЕ`, `6. Выполнение плана`.
- `wagons_excel` определяется по листам: `Сводка ПРОМ`, `Отчет НС`, `Наличие в Сургуте`, `Лист1`.
- `scanned_pdf` может определяться для PDF-файлов, если они будут добавлены через технический слой, но для штатного комплекта PDF не требуется.

Если локальная база от старой MVP-схемы несовместима с текущей структурой, приложение сохраняет ее рядом как `storage/station_crm_legacy_*.db` и создает новую базу.

## Продуктово-вагонная аналитика

Сервис не считает общий парк вагонов достаточным. Для каждого продукта MVP сравнивает:

- есть ли продукт на ЗСК;
- какой план налива;
- сколько есть вагонов под этот продукт;
- сколько годных и негодных;
- сколько погружено, оформлено и отправлено.

Справочник групп в коде:

- `СУГ`: ПБТ, ПБА, ПТ, ПТ ГОСТ, ПА, ФБ, БТ, ШФЛУ, ПГФ, УВФ;
- `СНП`: ДТ, ТС, АИ-92, АИ-95, ДГКЛ;
- `ТНП`: СК, темные нефтепродукты;
- `МЕТ`: Метанол;
- `МТБЭ`: МТБЭ.

Dashboard показывает таблицу продуктовых статусов: `норма`, `дефицит продукта`, `дефицит подходящих вагонов`, `много негодных`, `отстает оформление`, `отстает отправление`, `нет данных`.

Блок `Ложная обеспеченность парком` появляется, когда общий парк по группе выглядит достаточным, но по конкретному продукту не хватает годных вагонов.

## Графики dashboard

Dashboard использует Chart.js и показывает:

- воронку движения вагонов;
- сравнение день / ночь;
- погружено против оформлено по продуктам;
- структуру парка вагонов;
- продуктово-вагонную матрицу;
- топ-5 причин отклонений.

Если данных для графика мало, вместо графика показывается заглушка `Недостаточно данных`.

## Управленческий вывод

Сервис `app/services/insight_service.py` формирует rule-based вывод по комплекту:

- главный разрыв;
- риск;
- причина;
- что контролировать в следующую смену.

Правила учитывают разрывы между погрузкой, оформлением и отправлением, низкие коэффициенты оформления/вывоза, ложную обеспеченность парком и неравномерность смен.

Сервис `app/services/ai_summary_service.py` добавляет необязательную интеграцию с OpenAI API. Если `OPENAI_API_KEY` отсутствует или `USE_AI_SUMMARY=false`, используется rule-based вывод.

Сервис `app/services/ai_extraction_service.py` добавляет необязательный AI-разбор данных из уже сохраненных `raw_extracted_rows`. Если `OPENAI_API_KEY` отсутствует или `USE_AI_EXTRACTION=false`, приложение не падает, а AI-разбор помечается как skipped.

Настройки в `.env`:

```env
OPENAI_API_KEY=
USE_AI_EXTRACTION=false
USE_AI_SUMMARY=false
OPENAI_MODEL=gpt-5.4-nano
```

Для AI-summary в модель передаются только рассчитанные JSON-показатели: цепочка, коэффициенты, продуктово-вагонные метрики и статусы. Сырые файлы и сырые строки отчетов в OpenAI API не отправляются.

Для AI-extraction в модель передаются только уже найденные строки из `raw_extracted_rows`, без исходных Excel/PDF-файлов. Модель обязана вернуть строгий JSON, не придумывать цифры и указывать `source_rows`.

## Тренды

Страница `/trends` показывает динамику по всем загруженным `report_packages`:

- тренд по дням: прибыло на Промышленную, погружено, оформлено, отправлено в Сургут;
- тренд коэффициентов: сквозной коэффициент обработки, коэффициент оформления, коэффициент вывоза;
- тренд парка: груженые, порожние, негодные, не включенные в сводку;
- тренд по продуктам: погрузка и оформление.

Фильтры:

- дата с / по;
- продукт;
- смена: день, ночь, сутки.

Если загружен только один день, страница показывает сообщение: `Для трендов загрузите отчеты за несколько дат`.

## MVP-аналитика цепочки

Дашборд показывает воронку:

```text
Сургут -> Прибыло на Промышленную -> Обработано -> Погружено -> Оформлено -> Отправлено в Сургут
```

Для первичного заполнения `daily_chain_metrics` сервис ищет строки:

- в `wagons_excel`: `Наличие в Сургуте`, `Прибыло за смену`, `Прибыло за сутки`, `Отправлено за смену`, `Отправлено за сутки`, `Парк всего`, `Груженые`, `Порожние`, `Негодные`;
- в `operational_excel`: `Суточный факт`, `Суточное оформление РЖД`, `Факт нарастающим итогом`, `До конца месяца налить`.

Если число в строке не найдено, значение метрики остается `NULL`, но попытка сохраняется в `raw_metrics` со ссылкой на файл, лист и строку.
